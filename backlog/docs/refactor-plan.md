# Education Tree System 重构计划

## 重构背景

基于代码审查分析，项目虽然实现了业务模块分包和代码职责分层，但在组件抽象复用、代码组织和样式管理方面存在改进空间。

### 发现的主要问题

1. **工具函数重复定义**：`formatDate` 等函数在至少 3 个组件中独立定义
2. **大型组件文件**：存在 1500+ 行的组件文件，违反单一职责原则
3. **Props 类型分散**：每个组件独立定义 Props 接口，缺少统一管理
4. **API 层冗余**：`modules/*/api/` 层只是简单转发调用，没有提供额外价值
5. **样式和逻辑混合**：Tailwind 类名与业务逻辑混在一起，可读性差

## 重构原则

### 1. 单一职责原则 (SRP)
每个组件、函数只负责一个明确的功能。大组件应拆分为容器组件和展示组件。

### 2. 开放封闭原则 (OCP)
组件应对扩展开放，对修改封闭。通过 Props 和组合而非修改内部实现来扩展功能。

### 3. DRY 原则 (Don't Repeat Yourself)
消除重复代码，将公共逻辑提取到共享工具函数或自定义 Hooks。

### 4. 关注点分离
- 展示逻辑 → 展示组件
- 业务逻辑 → 自定义 Hooks
- 样式 → 设计系统组件
- 类型定义 → 独立 types 文件

### 5. 渐进式重构
优先重构低风险、高收益的部分，避免大规模破坏性改动。

### 6. 向后兼容
重构过程中保持对外接口稳定，不影响现有功能。

## 重构阶段规划

### 阶段 1：基础设施优化（1-2周）

**目标**：建立良好的代码基础设施，消除最明显的重复。

**预期成果**：
- 工具函数复用率 > 90%

## 风险与应对

### 风险 1：重构影响现有功能

**应对措施**：
- 每个任务完成后进行完整的功能测试
- 关键功能人工回归测试
- 保持小步快走，及时发现问题

### 风险 2：重构周期过长影响业务开发

**应对措施**：
- 采用渐进式重构，不阻塞业务需求
- 优先重构独立模块，减少影响面
- 新需求优先使用新架构实现

### 风险 3：团队成员不熟悉新架构

**应对措施**：
- 编写详细的开发指南
- 代码审查时及时指导
- 定期分享重构经验

## 时间安排

**总计：6-9 周**

- 第 1-2 周：阶段 1（基础设施优化）
- 第 3-5 周：阶段 2（组件职责分离）
- 第 6-7 周：阶段 3（模块架构优化）
